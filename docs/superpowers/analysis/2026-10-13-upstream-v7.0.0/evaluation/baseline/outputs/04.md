## Choir practice aid — draft neutral spec

**Status:** draft; written-artifact approval pending. **Track:** greenfield. **Frontend packet status:** required-pending.

Build a small practice aid for the user's mother on the tablet she already owns. The first experiment succeeds when she can start a rehearsal without help. It supports one journey: choose a song, read a short practice prompt, mark today's attempt, and view the last seven days. The experience should feel calm and welcoming after a missed day.

### Direction and assumptions

Use a simple tablet web app with HTML, CSS and JavaScript, with data stored locally. These are delegated implementation choices, not user-approved platform facts. Assume her tablet can open the app in a browser; tablet/browser compatibility must be verified before implementation commits to this delivery shape. This is a small, reversible experiment; native delivery and a larger framework are deferred.

Assume a small supplied song list with one short prompt per song. Actual song names and prompts are a content dependency before the experiment can be used. Assume “today” follows the tablet's local date, and the history shows today plus the previous six dates. These assumptions remain visible for artifact review.

### Behavior and scope

- Selecting a song shows its practice prompt and an action to mark today's attempt. No scoring or judgment accompanies the action.
- Marking an attempt records that song for the current local date. Repeated marking of the same song on that date produces one record.
- The seven-day view shows recorded attempts. Days without a record remain neutral; no failure labels, broken streaks or catch-up requirements appear.
- Returning to the app on the same tablet/browser restores saved records when local storage remains available. Clearing local data may reset history; that loss is accepted for this experiment.
- If saving fails, do not claim the attempt was saved. Keep the practice prompt usable and explain the failure plainly.

Accounts, cloud sync, scores and notifications are out of scope. This slice does not add audio playback, song editing or rehearsal management.

### Draft copy and frontend handoff

Draft visible strings: “Choose a song”, “Today's practice”, “Mark today's attempt”, “Attempt saved”, “Last seven days”, and “No attempts recorded yet. Start whenever you're ready.” Save error: “Couldn't save your attempt. You can still practise.” Dates use the tablet's locale; song names are supplied content. Accessibility labels must describe each song selection, marking action and history date without relying on color. Copy acceptance checks must reject language that implies a missed day is a failure.

The separate frontend-direction session must settle tablet layout, reading hierarchy, touch interactions and selected, unmarked, saved, empty-history and save-error states. It inherits the calm tone and this behavior boundary. No detailed visual target is approved yet.

### Acceptance examples and validation

- Given the song list, selecting a song reveals its short prompt without requiring an account.
- Given an unmarked song today, marking the attempt shows confirmation and a record for today; marking it again does not duplicate it.
- Given an attempt followed by a missed day, the seven-day view retains the attempt and makes no negative claim about the missed day.
- Given retained local data, reopening in the same browser restores the history. Given cleared local data, it shows the neutral empty state.
- Given a failed save, the app displays the save error and does not show a false saved confirmation.

Verify the complete journey on her actual tablet, including readable text, usable touch controls and starting a rehearsal without assistance. Compatibility and supplied song/prompt content block usable delivery; they do not block review of this draft behavior spec.

# D. Research-supported choice with an applicability limit

**Finding:** ParcelKit 2.4 replays caller-provided entries after initialization; the caller must persist them. Browser memory alone does not survive process termination. **Source:** `fixtures/parcelkit-24.md`, “Restart”. **Applies/limits:** this matches our installed 2.4 version, but does not prove our application's recovery works; no crash-recovery test has run.

**Finding:** an optional persistent queue is documented for ParcelKit 4.0. **Source:** `fixtures/parcelkit-40.md`, “Storage”. **Applies/limits:** that capability applies to 4.0, which we cannot adopt this release. It does not support a recovery promise for 2.4.

I recommend persisting pending entries and replaying them on initialization, with a process-restart recovery check before promising recovery. That adds storage work, but addresses the release's stated requirement. The alternative is a narrower demo that explicitly leaves restart recovery unverified and outside its promise; it is faster, but does not satisfy the release requirement.

For tomorrow, should we prioritize **persistent entries plus verified restart recovery (recommended)**, or **a narrower demo with no restart-recovery promise**?

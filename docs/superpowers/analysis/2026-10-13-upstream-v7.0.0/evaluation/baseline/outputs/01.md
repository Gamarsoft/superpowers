# Personal choir practice aid — draft neutral spec

**Status:** Draft for review; no written-artifact approval yet. Track: greenfield. Frontend packet status: `required-pending`.

### Goal and first boundary

Help the user's mother start a rehearsal on the tablet she already owns without needing help. The first experiment supports choosing a song, reading a short practice prompt, marking today's attempt and viewing the last seven days. The experience should feel calm; a missed day carries no failure message, penalty or broken streak.

### Direction and explicit assumptions

Use a small browser-based aid with local storage as the proposed delivery shape. This keeps the experiment small and avoids accounts and installation overhead; a native app would offer deeper platform integration at a higher setup cost. This is an author-selected assumption under the user's delegation, not a confirmed tablet capability.

The tablet's operating system and browser are unknown. Confirm basic browser and local-storage compatibility before implementation; if unsupported, revise the delivery assumption without changing the agreed behavior. Language, framework and internal structure are delegated to the builder.

For this draft, assume the aid is preloaded with a small set of songs and a short prompt for each. Song editing and importing are excluded from the first experiment. The actual song titles and prompts remain content dependencies before a usable rehearsal trial. Assume “today” and the seven-day window follow the tablet's local date; history is one attempted/not-marked record per song per day.

### Behavior and copy

The user chooses one song and sees its short practice prompt. She can select **“Mark today's attempt”** once for that song and date. Marking again does not add another attempt. The seven-day view includes today and the previous six local dates for the selected song. Switching songs shows that song's prompt and history.

Marked days say **“Practiced”**; unmarked days say **“No attempt marked”** without implying failure. After marking, show **“Today's attempt is marked.”** Avoid scores, streaks, red failure indicators or comparative performance language.

Store attempts only on this tablet. Reopening preserves them when local storage remains available. If saving fails, do not show a saved confirmation; show **“Couldn't save today's attempt. Try again.”** Clearing local data may remove history, which is acceptable for this experiment. An empty history still offers the practice prompt and today's action.

Use readable song names, explicit button labels and accessible names matching visible actions. Format history dates in the tablet's locale. Check long titles, translation expansion and text scaling during frontend direction. Loading, selection and storage-error states must be covered; accounts, permission dialogs and destructive controls are outside this slice.

### Acceptance examples

- With no attempts saved, she can choose a song, read its prompt and mark today without setup or help.
- Marking a song twice today produces one marked day.
- A missed day remains neutrally unmarked; today's practice is still available.
- Switching songs displays the selected song's prompt and seven-day history.
- After reopening with storage intact, saved attempts remain visible.
- If storage cannot save an attempt, the aid shows the retry message and does not claim success.
- In a trial on her tablet, she starts a rehearsal without assistance. This is the success signal; opening the aid alone is insufficient.

### Boundaries and remaining work

No accounts, cloud sync, scores, notifications, song editor or broader teaching system. No existing code or migration is involved. Tablet compatibility, song content and the stated date/history assumptions remain visible for review. Screen hierarchy, touch interaction and visual direction require a separate approved frontend packet before routing or UI implementation. This draft does not select a delivery workflow.

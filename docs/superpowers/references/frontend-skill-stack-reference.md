# Frontend skill stack

`superpowers:frontend-direction` accepts an approved neutral spec/follow-on or a standalone screen-improvement request. Substantial composition uses Paper with supported content and existing anchors. Interaction or component-sensitive feasibility uses a focused actual-app slice. Routine corrections stay in code. Start with one recommendation; add comparison for a consequential tradeoff or explicit request. Explicit image-concept and Companion mockup requests override the default medium for their scoped task.

Preserve task-to-layout reasoning and substantive design-knowledge consultation. Explain the observed problem, supported facts, chosen relationship and cost, then what visual/runtime evidence established. Critique actual design quality before approval. A polished composition or exact export alone does not show task improvement.

`superpowers:implementing-frontend-design` consumes the exact approved v2 packet in the active implementation workflow. It translates direct structure/style/token/asset evidence into project components, checks runtime fidelity and retains independent fresh-context visual review for non-trivial UI. It does not require GSD context or restart discovery.

Impeccable can supply focused assessment when installed. Its absence is not a prerequisite failure. Requirements, accessibility, retained brand/shell and the approved feature delta govern their scopes under [design authority](../../../skills/frontend-direction/references/design-source-priority.md). Existing UI does not veto an approved redesign.

Current packets use `--frontend/packet.md`, first-line `<!-- frontend-packet: 2 -->`, integer `schema_version: 2`, a screen/state index, conditional brownfield inspection, a `design_source` manifest under `design/`, separate `runtime_evidence`, scoped `references/` and nonbinding `history/`. See the [schema](../../../skills/frontend-direction/references/packet-schema.md) and [finalization recipe](../../../skills/frontend-direction/references/packet-finalization.md). Bind the extracted payload and recoverable runtime code, including dirty changes. The helper checks consistency and identity, not real execution, approval or quality.

The complete [handoff record](../../../skills/frontend-direction/references/packet-handoff.md) carries the producing entry, expected revision/descriptor hash, human approval reference, status and limits unchanged through spec, review, adapter and task. Missing/unsupported versions fail closed. Version 1 returns exactly: `Unsupported packet schema version 1. This workflow requires version 2; historical packets are reference material only.` No compatibility, conversion, migration or legacy fallback. Historical packets and their paths remain untouched reference material.

[Paper operating guidance](../../../skills/frontend-direction/references/paper-workflow.md) handles current tool inspection, direct extraction and immutable local snapshots. [Library upkeep](../../../skills/frontend-direction/references/paper-library.md) starts with useful coverage and maintains affected entries within allowance. Pending entries retain last verified revision/source/evidence. Report verified app delivery separately from upkeep; housekeeping cannot waive application defects or block an otherwise verified delivery.

Brainstorming retains Companion explanations, flows and product comparisons with consent, full startup and artifact-first/question-tool guarantees. Screen composition routes to Paper even after Companion consent. Temporary Companion files remain decision context. Required frontend direction stays `required-pending` until final approval before delivery routing. Standalone work keeps its original design-only or implementation scope.

Default adoption needs fresh regression/behavior evidence and a real pilot proving the full v2 path, scoped reconciliation, fidelity and useful upkeep within agreed effort. Passing scripts or time tracking alone does not activate the workflow. One-screen results do not establish long-term savings.

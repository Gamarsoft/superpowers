# Brownfield frontend contract workflow

Inspect the actual feature, relevant source/tokens and affected library entries. Separate supported behavior, retained brand/shell and technical/accessibility constraints from accidental defects and weak composition. Missing mappings mean unknown freshness; unrelated changes do not invalidate every entry.

Use frontend-direction directly for bounded screen improvement, or consume the approved neutral spec/follow-on. Apply task-to-layout and relevant substantive design knowledge before substantial Paper composition. Start with one recommendation using supported content; compare only consequential unresolved tradeoffs or an explicit request. Use focused actual-component slices for behavior or visual feasibility risks, not a complete second composition. Honor explicit medium overrides and keep their limits visible.

Critique hierarchy, grouping, useful density, type, spacing, alignment, contrast, action clarity, recovery, copy, accessibility and relevant reflow. Keep task/content/container widths comparable. Record observed problem, task impact and correction. Final design approval, agent functional checks and observed human use are distinct; optional human observation does not become an extra gate.

The v2 packet binds exact design extraction, frozen tokens, assets, copy and component mappings separately from recoverable runtime evidence and all seven runtime handoff fields. Carry the complete producing entry, expected revision/hash, human approval reference, status and limits unchanged through spec, review, adapter and task. Historical packets remain untouched reference material only. Missing/unsupported versions fail closed under the shared schema, with no compatibility, conversion or migration.

After approval, brainstorming returns to its delivery route. Standalone work retains its original scope without another routing ceremony. Implement using project components and direct extraction, then compare the rendered app against exact targets and perform independent fresh-context visual review. Provide served source/build identity, launch, readiness, authentication/state setup, viewports and server lifetime; screenshots alone cannot establish provenance or behavior.

Preserve manual/concurrent edits through a comparison with the last verified baseline. Reconcile only affected library entries after meaningful verified UI changes, within the agreed allowance. Deferred entries retain last verified revision/source/evidence and record pending change, reason and intended verified app revision. Report application completion and upkeep separately; pending housekeeping cannot block verified app delivery or waive defects and required proof. See [library upkeep](../../../skills/frontend-direction/references/paper-library.md).

Fixture evidence proves its exercised scope, not backend integration. Missing required evidence stays provisional unless explicitly accepted under the existing degraded mechanism. Optional critique tools do not override approval. Workflow adoption remains separate until a real pilot proves fidelity and useful scoped reconciliation within allowance.

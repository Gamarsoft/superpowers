# Proposed revision

## Next design decision

Explore a focused version of B for repeated work, with A retained as the baseline. On desktop, place a compact, always-visible `Vérification` panel beside the form. It summarizes the customer, adjustment effect, parking, reason, and note, but it is not a required step and does not gate saving. `Voir l'aperçu` remains optional.

This applies Refactoring UI by giving the form one primary action and muting supporting context. It applies the DOET mapping and feedback guidance by keeping credit/debit beside the positive amount and showing their combined effect in the summary. The prototype should establish whether the second column helps operators check entries without adding scan cost. With no task study, do not claim that B is faster.

The warehouse side panel is not approval for this dialog. That tool supports repeated total-to-record comparison; this task does not. Reuse its approved shell conventions only if shared, not its layout decision.

Use French currency and number formatting for `{newBalance}`. Announce outcome messages to assistive technology, move focus to the outcome heading, and associate confirmation errors with the checkbox.

## Keep and remove

Keep the positive amount field; adjacent `Crédit` / `Débit` choice; customer name and ID once in the dialog header; current balance; parking; reason; required note; confirmation; optional preview; save. Keep the signed effect once in `Vérification`, labelled `Effet sur le solde`, rather than beside the input and again in review.

Remove the audit subtitle and the note character count because neither helps this task. Do not show `status`, `writeAudit`, `correlationId`, `TRANSPORT_FAILURE`, or `retryKey` to operators. The stable request identity remains internal and powers `Réessayer à l'identique`.

Keep correlation ID and transport details in the engineer support console. Nothing supplied establishes an operator-to-support incident-reference procedure, so adding a copyable reference here would create a new product rule.

## Implementation and verification handoff

Build the proposed B variant with existing tokens and components. On narrow screens, place `Vérification` after the fields and before confirmation/actions. Preserve entered values through preview, refusal, and uncertain outcomes. Save must work without preview.

Verify keyboard order, visible focus, labels, positive-amount validation, required note and confirmation, French formatting, narrow reflow, and all five outcome states. Confirm that an unchanged retry reuses the internal request identity, a changed submission does not masquerade as that retry, and uncertain copy never implies success or failure.

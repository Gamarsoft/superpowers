## Décision proposée

Faire évoluer B en **formulaire avec récapitulatif latéral compact et persistant**, à tester pour le travail répété. La colonne principale conserve l’ordre d’action : montant positif → crédit/débit → parking → motif → note → confirmation. Le panneau aligne seulement les faits à vérifier avant l’enregistrement : client, parking, motif et impact signé. Il ne devient ni une étape séparée ni un prérequis : l’aperçu reste facultatif et `Enregistrer l’ajustement` reste directement disponible lorsque les champs requis sont valides.

Cette direction applique la hiérarchie, le regroupement et l’alignement consultés dans Refactoring UI, ainsi que les mappings, contraintes et retours d’état de DOET. Son coût est une largeur réduite pour le formulaire et une répétition ciblée. Le prototype doit donc vérifier les libellés longs, une faible hauteur et le repli mobile du récapitulatif sous le formulaire. Sans étude d’usage, on ne prétend pas qu’elle accélère le travail. Le panneau approuvé de l’outil d’entrepôt ne vaut pas approbation ici : il répond à une comparaison répétée de totaux, absente de cet ajustement.

## Texte français

| État | Texte |
|---|---|
| Normal | Titre : `Ajuster le solde` · Champs : `Montant`, `Type d’ajustement` (`Crédit`, `Débit`), `Parking`, `Motif`, `Note` · Aide montant : `Saisissez un montant positif.` · Actions : `Voir l’aperçu`, `Enregistrer l’ajustement`, `Annuler` |
| Aperçu | Titre : `Aperçu de l’ajustement` · Lignes : `Client`, `Parking`, `Motif`, `Solde actuel`, `Impact sur le solde`, `Note` · Aide : `Vérifiez ces informations avant d’enregistrer.` · Action : `Fermer l’aperçu` |
| Confirmation | Case : `Je confirme que cet ajustement doit être appliqué au solde de ce client.` |
| En cours | `Enregistrement de l’ajustement…` |
| Succès | Titre : `Ajustement enregistré` · Corps : `Le nouveau solde est de {newBalance}.` · Action : `Fermer` |
| Refusé | Titre : `Ajustement non enregistré` · Corps : `Vérifiez les informations saisies, puis réessayez.` · Actions : `Revenir au formulaire`, `Annuler` |
| Résultat incertain | Titre : `Résultat de l’enregistrement incertain` · Corps : `La réponse a pris trop de temps. L’ajustement a peut-être été enregistré. Ne modifiez pas les informations avant de réessayer.` · Actions : `Réessayer à l’identique`, `Fermer` |

Dates, nombres et monnaie suivent la locale française ; `{newBalance}` est formaté comme montant, jamais concaténé. Les contrôles gardent des libellés visibles, un nom accessible et un focus perceptible.

## Éléments à garder ou retirer

**Garder :** montant positif ; choix crédit/débit ; solde actuel ; client (identifiant en secondaire, nom en principal) ; parking ; motif ; note requise ; confirmation ; aperçu facultatif ; enregistrement direct ; impact signé une seule fois dans le récapitulatif ; nouveau solde après succès.

**Retirer de l’interface opérateur :** sous-titre d’audit, second montant signé, compteur sans limite, `status=accepted`, `writeAudit=true`, `TRANSPORT_FAILURE`, `retryKey` et `correlationId`. L’identité de requête reste interne. Le `correlationId` demeure consultable dans la console support des ingénieurs ; aucun identifiant ni geste “copier pour le support” n’est ajouté sans procédure opérateur établie.

## Handoff implementation et vérification

Prototyper les deux colonnes avec états locaux, contenu long et repli étroit, puis faire valider cette direction avant intégration. En implementation, préserver les valeurs saisies après refus ou timeout, désactiver les doubles clics pendant l’enregistrement et réutiliser l’identité stable uniquement pour une relance inchangée. Vérifier clavier/focus, validation de la note et du montant, aperçu facultatif, enregistrement sans aperçu, annonce accessible de chaque résultat, formatage français et absence de diagnostics techniques. Les fixtures prouvent le comportement visuel ; l’intégration devra encore prouver persistance, idempotence et solde retourné.
